## 1. 무엇을 해달라는 것인가

사용자 요청은 두 갈래다.

> "추천 질문 그냥 목업으로 달아놨는데 관련이 있는 질문으로 바꿧으면 좋겠는데 그리고 ai가 대화패턴 인식해서 다음 추천 질문 3가지도 추천해주는 기능도 추가했으면 좋겠어"

| 갈래 | 내용 | 주된 작업처 |
|---|---|---|
| **A** | 대화를 시작할 때 나오는 첫 질문 네 개를, **그 할 일에 맞는 질문**으로 바꾼다 | 백엔드(데이터) + 프론트 |
| **B** | 대화가 오간 뒤 **AI가 흐름을 보고 다음 질문 세 개를 제안**한다 | 백엔드(LLM) + 프론트 |

A는 정해진 문구를 어디에 두느냐의 문제이고, B는 새 기능이다. **A를 먼저 끝내는 편을 권한다** — B가 실패하거나 늦어져도 A만으로 사용자 요청의 절반이 해결되고, B의 화면 자리를 A가 미리 만들어 두기 때문이다.

## 2. 지금 어떻게 되어 있나

### 화면

`Majung-Frontend/src/features/chat/views/ChatPopup.tsx`

```tsx
/**
 * 무엇을 물어야 할지 모르는 사람을 위한 첫 마디 (시안).
 *
 * **빈 입력창은 저리터러시 사용자에게 가장 어려운 화면이다.** 물어볼 것이 없어서가
 * 아니라 어떻게 물어야 할지 몰라서 멈춘다. 눌러서 보내면 되는 문장을 몇 개 둔다.
 */
const PRESETS = [
  "오늘 뭐 해야 해요?",
  "어디로 가면 돼요?",
  "무슨 서류가 필요해요?",
  "돈이 드나요?",
] as const;
```

이 네 개가 **모든 할 일에서 똑같이 나온다.** 사용자가 "목업"이라고 부른 것이 이것이다. 통장을 만들러 가는 사람에게도, 심리상담을 알아보는 사람에게도 같은 질문이 뜬다.

화면에 그리는 자리는 같은 파일 아래쪽이다.

```tsx
{/* 대화가 아직 없을 때만 낸다. 오간 뒤에는 화면을 좁히기만 한다 */}
{messages.length === 0 ? (
  <ScrollView horizontal ...>
    {PRESETS.map((preset) => (
      <Pressable onPress={() => onSend(preset)} ...>
```

**대화가 시작되면 사라진다.** B는 이 자리를 대화 중에도 쓰게 만드는 일이다.

### 서버와 주고받는 것

`Majung-Frontend/src/shared/utils/api.ts`의 `streamChat`이 SSE를 읽는다. 지금 다루는 이벤트는 다섯이다.

| 이벤트 | 데이터 | 핸들러 |
|---|---|---|
| `triage` | `{ routes: RouteOut[] }` | `onTriage` |
| `evidence` | `EvidenceEvent` | `onEvidence` |
| `text` | `{ delta: string }` | `onText` |
| `card` | `CardData` | `onCard` |
| `error` | `{ message: string }` | `onError` |
| `done` | (없음) | `onDone` |

프레임을 가르는 코드는 `dispatchFrame`이고, 모르는 이벤트는 `default: break`로 **조용히 버린다.** 즉 서버가 새 이벤트를 먼저 보내기 시작해도 옛 앱이 깨지지 않는다.

## 3. 갈래 A — 할 일에 맞는 첫 질문

### 어디에 문구를 두나

두 가지 길이 있다.

**A-1. 서버가 할 일 카드에 담아 보낸다** (권고)

`IntakeTask`(`src/shared/types/intake.ts`)에 필드를 하나 늘린다.

```python
# 서버 응답에 추가
"starter_questions": ["통장은 어디서 만들어요?", "압류가 걸려 있어도 되나요?", ...]
```

- **왜 이쪽인가**: 질문 문구는 그 제도의 실제 내용에 매여 있다. "압류가 걸려 있어도 되나요?"는 통장(R10)에서만 뜻이 통한다. 제도 데이터(`institutions.json`)를 손보는 사람이 질문도 같이 손보는 편이 어긋날 여지가 적다
- 비어 있으면 프론트가 지금의 네 개로 물러선다. **필드가 없어도 앱이 깨지지 않게 한다**

**A-2. 프론트에 `RouteId`별 상수로 둔다**

- 서버를 안 건드려도 되지만, 제도 내용이 바뀔 때 프론트를 함께 고쳐야 한다는 것을 아무도 기억하지 못한다
- 급하면 이쪽으로 시작하고 나중에 A-1로 옮겨도 된다

### 문구를 쓸 때 지킬 것

- **`copy-voice.md`를 읽고 쓴다.** 이 자리는 **사용자가 하는 말**이므로 합니다체가 아니라 지금처럼 해요체 대화투다 ("돈이 드나요?"). 시스템이 하는 말과 갈래가 다르다
- 화면에 **"죄목"**을 쓰지 않는다. "수용 사유"는 써도 된다 (2026-08-31 결정)
- 짧게 쓴다. 칩 하나가 한 줄을 넘기면 가로 스크롤에서 읽히지 않는다
- 항목당 3~4개면 충분하다. 다섯을 넘으면 고르는 일 자체가 부담이 된다

## 4. 갈래 B — AI가 다음 질문을 제안한다

### 제안하는 계약

SSE에 이벤트를 하나 더한다.

```
event: suggestions
data: {"questions": ["신청하면 언제 나와요?", "안 되면 어떻게 해요?", "다른 지원도 받을 수 있나요?"]}
```

- **`done` 직전에 보낸다.** 답변 본문이 다 흐른 뒤라야 그 답을 보고 이어서 물을 것이 정해진다
- **개수는 정확히 셋이다.** 사용자가 셋을 원했고, 화면 폭에도 셋이 맞는다. 넘게 오면 프론트가 앞의 셋만 쓴다
- 못 만들었으면 **이벤트를 보내지 않는다.** 빈 배열을 보내면 프론트가 "빈 칸"과 "없음"을 가리지 못한다

### 프론트에서 손댈 자리

| 파일 | 할 일 |
|---|---|
| `src/shared/types/api.ts` | `ChatStreamHandlers`에 `onSuggestions?: (questions: string[]) => void` 추가 |
| `src/shared/utils/api.ts` | `dispatchFrame`의 `switch`에 `case "suggestions"` 추가 |
| `src/features/chat/hooks/useTaskThreads.ts` | 받은 질문을 방별로 담는다. **새 질문이 오면 앞의 것을 버린다** — 쌓으면 대화 아래에 옛 제안이 계속 남는다 |
| `src/features/chat/views/ChatPopup.tsx` | `messages.length === 0` 조건을 고쳐, 대화 중에도 제안이 있으면 칩을 낸다 |

**칩을 어디에 둘지가 화면 결정이다.** 지금은 입력창 바로 위다. 그대로 두면 답변을 읽고 눈을 내렸을 때 자연스럽게 만난다. 마지막 답변 말풍선 아래에 붙이는 안도 있는데, 그러면 대화를 거슬러 올라갈 때 옛 제안이 함께 보여 혼란스럽다. **입력창 위를 권한다.**

### 반드시 지킬 것 — 보안

이 서비스의 1번 규칙이 보안이다 (루트 `CLAUDE.md`).

- **대화 내용은 민감정보다.** 추천 질문을 만들려고 대화를 LLM에 다시 보낸다면, **§9.3의 마스킹을 그대로 거쳐야 한다.** 답변 생성 경로가 이미 마스킹을 거치고 있다면 같은 함수를 쓴다 — 두 벌로 두면 한쪽만 고치게 된다
- **서버 로그에 추천 질문 생성용 프롬프트를 남기지 않는다.** 그 안에 사용자 원문이 들어 있다
- 새 외부 의존성을 넣어야 한다면 **사용자 확인을 먼저 받는다**

### 반드시 지킬 것 — 내용

- **AI가 만든 질문이 곧 답이 되어서는 안 된다.** "긴급지원은 3일 안에 나와요"처럼 사실을 담은 문장을 질문 자리에 넣으면, 사용자는 그것을 확인된 안내로 읽는다. 질문은 질문으로 끝나야 한다
- **제도를 지어내지 않게 한다.** "○○지원도 받을 수 있나요?"에서 ○○이 없는 제도면, 눌렀을 때 "그런 것은 없어요"가 돌아온다. 지원 항목 목록(R1~R4·R6~R15, **R5는 결번**) 안에서만 고르게 프롬프트를 묶는 편이 안전하다
- 어체는 A와 같다. 사용자가 하는 말이므로 해요체다

## 5. 검증

프론트에는 화면 검증(Playwright)이 이미 있다. `Majung-Frontend/e2e/chat.spec.ts`가 채팅 팝업을 다룬다.

```bash
cd Majung-Frontend
npm run e2e                 # 화면 검증 (35개)
npm test                    # 계산 검증 (117개)
npx tsc --noEmit            # 타입
```

가짜 서버 응답은 `e2e/support/app.ts`가 만든다. `suggestions` 이벤트를 흘려보내려면 그 파일의 `chatDeltas` 옆에 `chatSuggestions`를 더하고, SSE 본문에 프레임을 하나 끼우면 된다.

```ts
const body =
  deltas.map((delta) => frame("text", { delta })).join("") +
  (mocks.chatSuggestions ? frame("suggestions", { questions: mocks.chatSuggestions }) : "") +
  frame("done", {});
```

**넣었으면 좋을 검증**

- 답이 다 온 뒤 제안 셋이 뜬다
- 제안을 누르면 그 문장이 그대로 질문으로 나간다
- 새 답변이 오면 앞의 제안이 사라지고 새것으로 바뀐다
- 서버가 제안을 안 보내면 칩 자리가 아예 생기지 않는다 (빈 띠가 남지 않는다)

**시계를 고정한 채로는 애니메이션이 있는 화면을 다루지 못한다.** `openApp`에 `freezeClock: false`를 넘겨야 한다 — React Native의 `Animated`가 흐른 시간을 `Date.now()`로 재기 때문이다. 이 함정에 한 번 빠져서 적어 둔다.

## 6. 아직 정해지지 않은 것

넘기는 쪽에서 판단하지 않고 남긴다.

1. **A를 A-1로 갈지 A-2로 갈지** — 서버 계약을 늘릴지 프론트 상수로 둘지
2. **첫 질문 문구를 누가 쓰는지** — 지원 항목이 14개이므로 40~50개 문장이 나온다. 제도 내용을 아는 사람이 쓰는 편이 맞다
3. **B의 제안을 저장할지** — 지금 계획은 화면에만 두고 버리는 것이다. 저장하면 보관·파기 대상(§9.4)이 그만큼 는다. **저장하지 않기를 권한다**
4. **B가 실패했을 때 A의 첫 질문으로 되돌아갈지** — 대화 중에 제안이 없으면 칩 자리를 비우는 편이 단순하다
