## 1. 이 개편의 성격

예선 코드는 **5탭 네비게이션** 구조였다. 본선은 **단일 화면 + 아코디언** 구조다. 정보 구조가 근본적으로 다르므로 **`src/` 아래 화면 코드는 대부분 새로 쓴다.** 기존 파일을 고쳐 쓰려고 하면 죽은 라우트와 안 쓰는 컴포넌트가 남는다.

다만 **설정 계층과 계약 계층은 그대로 살린다.** 아래 2절이 그 경계다.

#### `TaskCardView.tsx`를 살리는 이유

기획서 §4.1(결과 카드 구성)과 거의 그대로 맞는다. 주석에 **"순수 프레젠테이션(props-driven), 비즈니스 로직 없음"**이 명시되어 있어 §4.1의 제도 원본·판정 결과 분리 원칙과도 어긋나지 않는다.

| §4.1이 요구하는 것 | 현재 상태 |
|---|---|
| 제목 | `task.node_name` ✅ |
| 갈 곳 | `InfoRow "어디서"` ✅ |
| 준비물 | `InfoRow "준비물"` ✅ (없으면 "없음") |
| 소요 기간 | `InfoRow "기간"` ✅ |
| 기한 | 별도 배너 ✅ |
| 사유 | `priority_reason` ✅ **조건부 렌더** |
| **먼저 확인할 것** | ❌ 없음. KB 필드가 생기면 추가 (기획서 §12-14) |
| **연락처** | ❌ 없음. 서버가 붙인다 (§6.4) |
| **공식 제도명** | ❌ 없음. `공식 이름은 '~'예요` 형태 (§3.9-②) |

**빈 값 처리 패턴을 그대로 쓴다.** `priority_reason`·`deadline`·`summary_easy`가 전부 `{값 ? (<Text/>) : null}` 형태다. **자리를 잡아두고 비우는 것이 아니라 값이 있을 때만 요소가 생긴다.** 바깥 `View`가 `gap`으로 간격을 주므로 요소가 없으면 간격도 함께 사라진다.

기획서 §4.1이 **"사유는 선택 값이며 대부분의 카드에서 비는 것이 정상"**이라고 정했는데, 이 패턴이 그 요구를 이미 충족한다. 새로 짜지 말고 이대로 이어간다.

> ⚠️ **다만 색이 하드코딩되어 있다.** `#fff3e0`·`#9a5b00`·`#1d1b20`·`#494551`·`#7c7c7c`가 그대로 박혀 있고 `brand`와 `line`만 토큰을 쓴다. **팔레트 정리(3절) 때 함께 토큰화한다.** 기한 배너의 `#fff3e0`/`#9a5b00`은 오렌지 계열이라 `sun.100`/`sun.900`으로 옮기면 맞는다.

**버튼 둘도 그대로 쓸 자리가 있다.** "AI에게 물어보기"는 §6.1의 채팅 팝업 열기로, "완료"는 §5.2의 완료 처리로 이어진다. `isCompleting` 상태까지 이미 들어 있다.

## 3. 색 팔레트 (확정 — 네이비 유지)

프로토타입 HTML은 오렌지(`--brand: #f97316`)를 주 색으로 그려져 있으나 **주 색은 기존 네이비를 유지한다.**

| 역할 | 프로토타입 | 확정 토큰 |
|---|---|---|
| 주 색 | `#f97316` | **`brand` = `#024f9f`** |
| 주 색 배경 | `#fff3e8` | **`brand.soft` = `#e1eefa`** |
| 강조·포인트 | 오렌지 전반 | **`sun.500` = `#EF9F27`** · **`chip` = `#ffdcc0`** |

**프로토타입의 따뜻한 인상을 통째로 버리지 않아도 된다.** `tailwind.config.js`에 오렌지 계열 포인트 색이 이미 들어 있다. 주 색만 네이비로 되돌리고 강조를 이 토큰으로 옮기면 인상이 상당 부분 살아남는다.

- 인덱스 탭의 항목별 색(빨강·주황·노랑·초록·파랑·보라)은 **분류용이라 그대로 둔다.**
- `tailwind.config.js`에는 모바일용과 PC용 팔레트가 나뉘어 있는데, **PC용(navy·paper 계열)은 데스크톱 셸과 함께 정리 대상**이다.

## 8. 반드시 지킬 것

### 보안

1. **클라이언트 번들에 어떤 비밀도 넣지 않는다.** Claude API 키는 백엔드에만.
2. **자동 로그인 토큰은 `expo-secure-store`에.** `AsyncStorage`나 `localStorage`에 평문으로 두지 않는다 (§2.4).
3. **위치 좌표를 서버로 보내지 않는다.** 기기에서 시군구로 바꾸고 좌표는 버린다 (§5.4). **Google Maps Geocoding API는 쓰지 않는다.**
4. **의존성을 추가할 때마다 "이게 어떤 데이터를 어디로 보내나"를 확인한다.** 사용자 확인이 필요하다.
5. **개인정보를 로그에 남기지 않는다.**

### 톤

기획서 §3.9에 **화면 문구·문항 구성 규칙 11개**가 있다. 화면에 나가는 모든 한국어가 대상이다. 특히:

- **판단하는 어감을 쓰지 않는다.** "기한을 넘겼나요" → "기한은 지났나요"
- **쉬운 말과 공식 명칭의 역할을 나눈다.** 문항에 괄호로 공식 명칭을 넣지 않는다
- **선택지는 1인칭 진술.** 단 죄목 대분류는 예외 — 명사형을 유지한다
- 저리터러시 사용자 전제. **큰 글씨, 한 문장에 한 가지**
