### B-3. R2 매핑 정정 지시

두 가지를 개발 세션에 지시했다.

1. `welfare-emergency-support`(정부 긴급복지)의 `route_ids`를 **`["R2", "R12"]`로 넓힘.** 기획서 검수표 R12 행이 "129 정부 긴급복지·R2 공단 긴급지원 병렬 안내"라고 명시
2. **`welfare-koreha-emergency`(공단 긴급지원) 항목을 새로 추가.** R2의 이름은 "공단 긴급지원"인데 매칭되는 KB가 정부 제도 하나뿐이었다

### B-4. R3·R7 KB 항목 신규 작성

공단 공식 페이지 근거로 두 항목을 만들어 개발 세션에 넘겼다. `health-koreha-basic`과 `startup-koreha-support`다.

**금액과 조건을 `summary_easy`에 넣지 않았다.** 창업지원은 공식 조건이 여섯 가지이고 지원 내용도 연이율 2.5%·최대 5천만원·최대 6년·본인부담 50% 이상으로 복잡하다. 사용자가 알 수 없는 것을 문항에서 묻지 않기로 했으므로 조건은 결과 카드의 "먼저 확인할 것"에서 다룬다. **다만 본인부담금이 있다는 사실만 요약에 남겼다.** 이걸 모르고 상담을 가면 헛걸음이 된다.

공단 긴급지원도 같은 이유로 금액을 넣지 않았다. 기부금 재원이라 지부 사정에 따라 달라지고, 숫자를 화면에 내려면 "최대·공식 페이지 기준·확인일" 표시가 함께 가야 한다.

### B-5. 항목별 대표 제도를 `is_lead` 필드로 명시

개발 세션이 문제를 찾았다. **`_match_cards`는 항목당 제도를 하나만 뽑고, 그 하나를 배열 순서로 정한다.** 그래서 KB 항목을 추가하는 것만으로는 R2에 공단 제도가 나오지 않았다. 같은 문제가 R6과 R10에도 있었고, **R10에서는 통장이 아예 없는 사람에게 "통장 정지 풀기"가 나가고 있었다.**

개발 세션이 배열 순서로 임시 해결하고 회귀 테스트를 넣었다. 여기에 더해 **`is_lead` 필드를 지금 넣기로 했다.** 세 가지 이유다.

1. 배열 순서는 조용히 깨진다. 나중에 제도를 추가하는 사람이 왜 순서가 중요한지 모른 채 정렬할 수 있다
2. 한 제도가 여러 항목에 걸릴수록 순서 하나로 여러 항목을 동시에 만족시켜야 한다. R12에서 이미 어려움이 나타났고, 제도가 늘면 불가능한 배치가 생긴다
3. **버려지는 작업이 아니다.** 나중에 항목당 여러 장을 뽑게 되어도 "첫 장이 무엇인가"는 여전히 필요하다

**항목당 여러 장을 뽑는 것은 화면 개편 때로 미뤘다.** 방향은 그쪽이 맞다. 기획서에 병렬 안내가 여러 곳에 있다(R12의 "정부 긴급복지·공단 긴급지원 병렬", R15의 "R3·119 병렬"). 다만 SSE 계약과 화면 표현이 함께 바뀌는 일이다.

### B-6. KB 스키마 확장 기준을 `RouteResultCard`로 고정

창업지원의 여섯 요건을 담을 자리가 지금 KB 스키마에 없다는 지적이 나왔다. **새로 설계하지 않는다.** `15개 질문` 기획서의 개발 계약에 `RouteResultCard` 인터페이스가 이미 정의되어 있다.

`eligibilitySummary`·`benefitAmountOrDuration`·`cautions`·`applicationSteps`·`sourceUrls`·`verifiedAt` 등이 들어 있다. **다음 작업에서 붙이기로 한 `source_url`·`fetched_at`이 바로 `sourceUrls`·`verifiedAt`이다.**

지금 KB 스키마는 예선용 경량판이고 본선 계약은 훨씬 넓다. **스키마를 확장할 때 임의로 필드를 만들지 말고 이 인터페이스에 맞춘다.** 그러면 화면 개편 때 다시 고칠 일이 없다.

단, **이번 커밋에는 넣지 않는다.** 지금 작업은 6영역 제거이고 커밋 승인을 기다리는 상태라, 범위가 섞이면 승인 판단이 어려워진다.

### B-7. `is_lead` → `lead_for`로 정정 (개발 세션 제안 수용)

내가 `is_lead` boolean을 지시했으나 **표현할 수 없는 상태가 있었다.** 정부 긴급복지지원제도는 R2와 R12 양쪽의 근거이지만 **어느 쪽의 대표도 아니다.** boolean이면 "자기 `route_ids` 전부에서 대표"가 되어 이 상태를 적을 수 없다.

개발 세션이 **"이 제도가 어느 항목의 대표인가"를 항목 목록으로 적는 `lead_for`**로 만들었다. 이쪽이 맞다.

```json
{ "id": "welfare-emergency-support", "route_ids": ["R2","R12"], "lead_for": [] }
{ "id": "identity-resident-registration", "route_ids": ["R9","R11"], "lead_for": ["R9"] }
```

주민등록 재등록이 R9의 대표이면서 R11의 근거이고 R11의 대표는 전입신고라는 관계가 이 형태로만 표현된다.

**검증을 테스트가 아니라 로더 부팅 시점에 넣은 것도 더 낫다.** 테스트만이면 데이터를 손으로 고치고 배포하는 경로에서 빠져나간다.

### B-8. KB 스키마와 판정 결과 DTO를 층으로 나눈다

내가 "`RouteResultCard`를 기준으로 맞추라"고 지시했는데 **뭉뚝한 문장이었다.** 개발 세션이 짚었다. `state`·`displayTier`·`taskStatus`·`matchedBecause`는 제도의 속성이 아니라 **"이 사용자에게 이 항목이 어떻게 판정되었나"라는 계산 결과**다. 한 구조에 담으면 `institutions.json`이 사용자별 상태를 들고 있는 모양이 된다.

두 층으로 나눈다.

**KB(제도 원본)** — `valueSummary`(=`summary_easy`) · `requiredDocuments`(=`docs`) · `benefitAmountOrDuration` · `eligibilitySummary` · `applicationSteps` · `cautions` · `sourceUrls` · `verifiedAt`

**판정 결과 DTO** — `routeId` · `state` · `displayTier` · `taskStatus` · `completedAt` · `resultVariant` · `matchedBecause`

`RouteResultCard`는 이 둘을 합쳐 화면에 내보내는 **조립 결과**이지 어느 한쪽의 저장 형태가 아니다.

### B-9. `132` 검증

사용자가 "그대로 해놔"라고 한 값이지만 확인했다. **맞는 번호다.** 대한법률구조공단, 국번 없이 132, 발신자 부담.

### B-6. `SSOT.md`와 리뉴얼 기획안의 관계

**층위가 아니라 시점이 다르므로 상하로 풀면 어긋난다.** 이렇게 정리했다.

### C-1. 위치 권한을 과도하게 경계했다

"위치 권한 팝업이 감시 경험을 환기시킨다"는 다른 세션의 의견을 **검증 없이 받아 확대했다.** 위치 권한 요청은 지금 거의 모든 앱이 띄우는 표준 절차이고, 이 사용자층에게만 다르게 읽힌다고 볼 근거가 없다. 팀이 실제로 인터뷰한 결과도 반대 방향("실질적 도움이 되면 개인정보 제공에 거부감 없음")이었다.

### C-2. 역지오코딩을 근거 없이 위험으로 제시했다

GitHub 이슈 제목만 보고 "신뢰성이 확실하지 않다"고 전달했다. **그 이슈의 현재 상태를 확인하지 않았다.** Expo 공식 문서를 확인하니 지원 중단 표시도 알려진 문제 안내도 없고, 반환값에 `city`·`district`·`region`·`subregion`이 포함되어 시군구가 그대로 나온다.

**교훈: 확인한 것과 추측을 구분해서 전달한다.**

### C-3. 프론트 범위를 3파일로 잘못 인계했다

실제로는 8파일이다. `AreaOut`이 챗 기능 전체에 퍼져 있었다. 특히 `MessageViews.tsx`의 `TriageBanner`가 `area.key`·`label`·`rank`·`reason`을 직접 렌더하는데, **타입만 바꾸고 렌더링을 두면 타입 검사는 통과하고 화면만 빈다.** 다른 세션이 전수 조사로 잡아냈다.

|---|---|
| 머리말 | 문서 관계 규칙 명시. `companions`에 새 계약 3개 추가, 옛 문서 2개는 `archived`로 분리 |
| §3 User Flow | 로그인 없는 3갈래 진입 → 가입 화면 + 기기 자동 로그인. 자유발화 → 6분야 문답 |

| §10 개인정보 | **전면 개정.** 수집·저장 정책을 표로 다시 쓰고, "저장하는 순간부터 출소자 명단이 실재한다"는 전제를 명시 |
| §11 L1 | 기관 데이터는 전국을 확보했다는 사실 반영 |
| §14 변경 이력 | 이번 개정 6건 기록 |

**옛 문서 두 개에도 경고를 붙였다.** 특히 `HANDOFF.md`가 **"새 세션은 이 문서부터 읽으라"**고
안내하고 있어서, 새로 붙는 세션이 7월 30일 상태를 현재로 알게 될 위험이 있었다. 읽을 순서를
`SSOT.md` → `intake-contract.md` → 이 결정 기록으로 바꿔 적었다.

**이것으로 "충돌하면 늦은 날짜가 이긴다"는 임시 규칙에 기대지 않아도 된다.** 대체된 항목마다
어느 문서를 따라야 하는지가 본문에 적혀 있다.
