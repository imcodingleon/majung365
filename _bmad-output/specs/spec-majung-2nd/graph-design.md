# 블로커 A — 선행조건 그래프 데이터 설계

> C7(의존 그래프 엔진)의 입력 데이터 계약. SSOT §8의 `[팀 확정]` 두 칸(제도 노드 수 · 선행조건 엣지 수)을 이 문서가 채운다.

## 1. 결정 요약

| # | 결정 | 이유 |
|---|---|---|
| 1 | **노드 = 자원(확보해야 할 것) 단일 타입.** 제도는 노드가 아니라 노드를 얻는 *경로* | 엣지가 `requires` 한 종류로 끝나고, 사용자 상태(O/X/△/?)가 노드에 1:1로 붙는다 |
| 2 | **경로(`obtain`)는 배열.** 한 자원에 여러 획득 경로 | 잘 곳은 공단 생활관으로도, 긴급복지 주거지원으로도 얻는다. 선행조건이 경로마다 다르다 |
| 3 | **경로는 상태별로 분기(`for_state`)** | 통장이 `X`면 "개설", `△`면 "정지 해제". 장소·서류가 다르다. SSOT §6.2가 말한 "△가 이 도메인의 특이점"이 데이터에서 실체를 갖는 지점 |
| 4 | **엣지마다 `confidence` + `basis`** | `assumed` 필터가 곧 공단 인터뷰 질문지(§6). 미검증 값을 데이터 레벨에서 관리한다 |
| 5 | **코어 8 깊게 + 단말 4 얇게** | 순환은 신분·주거·긴급복지에서만 발생한다. 취업·의료·채무는 선행조건만 받고 후속 해금이 없어 검수 부담이 작다 |
| 6 | **카드 파일과 그래프 파일을 분리** | 카드는 사람이 읽는 문장, 노드는 엔진이 푸는 제약. 합치면 문구 수정이 그래프를 흔든다 |

**파일 배치**

| 파일 | 역할 | 상태 |
|---|---|---|
| `Majung-Backend/app/domains/knowledge/data/graph.json` | 노드 · 경로 · 선행조건 (C7 입력) | 신규 |
| `Majung-Backend/app/domains/knowledge/data/institutions.json` | 안내 카드 (C9 RAG · 응답 문구) | 기존 유지 · `kb_ref`로 연결 |

## 2. 스키마

```jsonc
{
  "id": "bank_account",
  "name": "본인 명의 통장",
  "route_ids": ["R10"],            // 이 자원이 근거가 되는 지원 항목들 (R1~R4 · R6~R15)
  "tier": "core",                  // core(엣지 조밀) | terminal(후속 해금 없음)
  "deadline": null,                // { "text": "...", "confidence": "...", "basis": "..." } | null
  "obtain": [
    {
      "for_state": ["X"],          // 이 경로가 유효한 사용자 상태
      "action": "은행에서 계좌 새로 만들기",
      "kb_ref": "identity-bank-account",
      "where": "가까운 은행 지점",
      "docs": ["신분증", "본인 명의 휴대폰(본인 확인에 쓰여요)"],
      "duration_days": 1,
      "requires": [
        { "node": "id_card", "confidence": "confirmed",
          "basis": "KB identity-bank-account docs: 신분증" }
      ]
    },
    {
      "for_state": ["BLOCKED"],    // △
      "action": "통장 정지 풀기",
      "kb_ref": "identity-bank-account",
      "where": "거래 은행 지점",
      "docs": ["신분증"],
      "duration_days": 1,
      "requires": [
        { "node": "id_card", "confidence": "assumed",
          "basis": "정지 사유(압류·대포통장 의심)별 절차 상이 — 공단 확인 필요" }
      ]
    }
  ]
}
```

**상태 코드**는 JSON에 글리프를 넣지 않는다 — `O` / `X` / `BLOCKED`(△) / `UNKNOWN`(?). 파싱·로그·정규식 검사에서 안전하다.

**엣지 평탄화.** 로더가 `obtain[].requires[]`를 `(from, to, path_index, confidence, basis)` 리스트로 펼친다. 엣지를 별도 배열로 두지 않는 이유는 "이 엣지가 어느 경로의 조건인지"를 잃지 않기 위해서다.

**유효 선행조건(위상 정렬 입력).** 노드의 유효 선행조건 = `for_state`가 현재 상태와 맞는 경로들 중 **미충족 선행조건이 가장 적은 경로**의 `requires`. 경로 수가 상수라 복잡도는 여전히 **O(V+E)**.

| id | 이름 | 폐기 사유 |
|---|---|---|

**엣지 15개** — 코어 13 · 단말 2. 이 중 **`confirmed` 6 · `assumed` 9**(§6).
경로 단위로 센다. `bank_account ← id_card`는 `X`(개설) 경로와 `△`(정지 해제) 경로에서 각각 한 번씩 잡히고, 두 엣지의 `confidence`가 다르다.

## 4. 그래프 형태

```
[진입차수 0 = 3개]
proof_of_release ●        mental_care ○        legal_aid ○
   │                      (전화만으로 가능)     (전화만으로 가능)
   ├──────────────► job_koreha ○
   │
   ├──► shelter ──► address ──► id_card ──┬──► bank_account ○
   │      ▲                        │       │
   │      └────────────────────────┘       │
   │        (경로② 긴급복지 주거지원)        │
   │                                       ├──► emergency_cash ⏰
   │                                       ├──► debt_workout ○
   │                                       └──► medical_aid ○
   └───────────────────────────────────────┘
                       (id_card는 proof_of_release도 요구)

● 순환 해제점   ○ 단말   ⏰ 기한 있음
```

`shelter → address → id_card → shelter`(경로②)가 순환이다. `proof_of_release`가 이 순환 밖에서 `shelter`(경로①)와 `id_card` 양쪽에 진입해 고리를 끊는다.

## 7. SSOT 정정이 필요한 항목

| 위치 | 현재 | 정정 |
|---|---|---|
| §6.4 | "수용증명서 — 그래프에서 **유일하게** 진입차수가 0인 노드" | 진입차수 0 노드는 **3개**다. `mental_care`·`legal_aid`는 전화 한 통으로 되고 서류가 없다. "유일하게 진입차수가 0인 **제도 노드**"로 정정. 오히려 서사가 세진다 — *"아무것도 없어도 오늘 할 수 있는 게 셋 있고, 그중 다음을 가장 많이 여는 것이 수용증명서다"* |
| §8 | 제도 노드 수 `[팀 확정]` / 선행조건 엣지 수 `[팀 확정]` | **노드 12 · 엣지 15** (confirmed 6 · assumed 9) |
| §6.6 | 케이스 3건 + `[팀 확정]` | 3건 모두 이 그래프에서 검증 통과(§5). 블로커 B에서 케이스를 확장한다 |

## 8. 범위 밖 (이번에 하지 않는 것)

- **지부·지자체별 조건 분기** — SSOT §11 L1. 서울 기준 단일 그래프만. 본선에서 노드에 지역 축 추가
- **엣지 가중치·확률** — 선행조건은 있거나 없거나다. 확률 모델은 과설계
- **점수·등급 산출** — SSOT §10 위반. 그래프는 "다음에 무엇을 할 수 있나"만 계산하고 사람에게 점수를 매기지 않는다
  > ⚠️ 기존 유저플로우 도식의 백엔드 블록에 "적합도 점수 산출" · "일정 점수 초과?"가 있다. SSOT §10("사용자에게 점수·등급·위험도를 부여하지 않는다")과 충돌한다. 도식 재작성(SSOT §12 순위 5) 때 정리 대상
- **`?`(모름) 상태의 능동적 해소** — SSOT §6.3 6단계대로 과제 제시 *후* 1건만 되묻는다. 사전 질문 확장은 하지 않는다
