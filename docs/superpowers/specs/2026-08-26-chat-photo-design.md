# 담당자 채팅에 사진 첨부 — 설계

> 마중365 본선. 기획서 §7.3·§9.2·§9.5, 소켓 계약 `Majung-Backend/docs/socket-contract.md`.
> 결정 기록: `_bmad-output/specs/spec-majung-2nd/decision-log-2026-08-26.md`

## 뒤집는 결정

`migrations/0005_visit_message.sql`에 이렇게 적혀 있다.

> **이미지를 넣지 않는다.** 참고 프로젝트에는 있지만 여기서는 신분증이나 서류 사진을
> 주고받게 되어 위험만 커진다. 텍스트만 주고받는다.

**팀 회의 결정으로 뒤집는다** (2026-08-26). 담당자가 "출소증명서 사진 보내 주세요"라고
하는 것이 실제 상담에서 일어나는 일이고, 그때 말로만 주고받게 두면 사용자가 창구까지
한 번 더 가야 한다.

**막았던 이유는 사라지지 않는다.** 서버에 출소자의 서류 사진이 쌓인다는 사실은 그대로이며,
그래서 아래 보관 규칙이 선택이 아니라 이 결정에 딸린 조건이다.

## 어디에 두는가

**Supabase Storage 비공개 버킷 `visit-photos`.** 새 업체가 아니다 — 이미 쓰는 Supabase의
다른 서비스이고, DB와 같은 프로젝트·같은 지역(서울)에 있다.

경로는 `{visitId}/{messageId}`다. 방 단위로 묶여 있어 방문 요청이 지워지면 그 앞자리를
통째로 지우면 된다.

## 암호화

**사진도 암호화해 넣는다.** 대화 본문을 암호화하는 것과 같은 판단이다 — 담당자 화면은
공용 기기일 수 있고, 오가는 것이 신분증이다.

`FieldCipher`는 문자열 전용이라 **바이트용 짝을 더한다.**

```python
def encrypt_bytes(self, plaintext: bytes) -> bytes: ...
def decrypt_bytes(self, stored: bytes) -> bytes: ...
```

같은 AES-256-GCM에 같은 키다. 문자열 쪽은 base64를 씌우는데 바이트 쪽은 씌우지 않는다 —
파일은 그대로 저장소에 올라가므로 33%를 부풀릴 이유가 없다.

**서버가 사진을 두 번 지나간다.** 올릴 때 한 번, 볼 때 한 번이다. EC2가 t4g.micro라
크기 상한이 그만큼 중요하다 (아래).

## 창구

### 올리기 — `POST /api/visits/{id}/photos` (multipart)

새 의존성 `python-multipart` 하나가 필요하다. FastAPI가 파일을 받으려면 있어야 하고,
**하는 일은 요청 본문 파싱뿐이라 데이터를 어디로도 보내지 않는다.**

받기 전에 거른다.

| 검사 | 왜 |
|---|---|
| 방 참여자인가 | 남의 방에 사진을 넣을 수 없다 |
| 방이 열려 있는가 | 닫힌 방은 글도 못 쓴다. 사진도 같다 |
| `image/jpeg` · `image/png` · `image/webp` | 선언한 형식만 받는다 |
| **5MB 이하** | 서버가 두 번 지나가므로 상한이 곧 비용이다. 폰 사진 한 장이 보통 2~4MB다 |

성공하면 `visit_message`에 `kind="photo"` 한 줄이 쌓이고 방 전체에 `new_message`가 나간다.
**대화의 한 줄이지 따로 관리하는 목록이 아니다** — 순서·읽음·삭제가 전부 대화 규칙을 탄다.

### 보기 — `GET /api/visits/{id}/photos/{messageId}`

서버가 방 참여자인지 확인하고, 저장소에서 받아 복호화해 그대로 돌려준다.

**서명 URL을 대화에 실어 보내지 않는다.** 소켓 페이로드에 URL이 박히면 만료를 관리할 수
없고 서버 로그에도 남는다. 메시지에는 `messageId`만 있고 화면이 그때그때 받는다.

응답에 `Cache-Control: private, max-age=300`을 붙인다. 같은 사진을 스크롤할 때마다
서버가 다시 지나가지 않게 한다.

## 저장 — 마이그레이션 `0011_visit_message_photo.sql`

약속 카드(`0010`)가 더한 `kind`에 값을 하나 늘린다.

```sql
alter table visit_message
  drop constraint if exists visit_message_kind_check,
  add constraint visit_message_kind_check
    check (kind in ('text', 'proposed', 'confirmed', 'cancelled', 'photo'));

alter table visit_message
  add column if not exists photo jsonb;
```

`photo`에 담기는 것:

```json
{ "path": "24702de6-.../e50af497-...", "bytes": 1843200, "mime": "image/jpeg" }
```

**평문이다.** 경로와 크기는 사진의 내용이 아니다. 내용은 저장소 안에서 암호화되어 있다.

## 보관과 파기

**대화와 같은 기간이다** (§9.5 — 방문 일정이 끝난 시점부터 3개월). 사진만 더 오래 두거나
덜 두지 않는다. 한쪽만 지우면 "지웠다"는 말이 반쪽이 된다.

- 계정을 지우면 (§9.4) `visit_request`가 지워지고 `visit_message`가 딸려 지워진다.
  **그런데 저장소 파일은 안 딸려 지워진다** — DB의 cascade는 Storage를 모른다.
  `delete_me`가 그 앞자리(`{visitId}/`)를 함께 지워야 한다
- 파기 배치는 `0005`가 적어 둔 그대로 아직 없다. 이번에도 만들지 않지만 **지워야 할
  대상이 파일까지 늘었다는 것을 여기 남긴다**

## 소켓

**새 이벤트를 만들지 않는다.** 약속 카드와 같은 판단이다 — `new_message`의 `kind`가
`"photo"`이고 `photo` 필드가 실린다.

```json
{
  "id": "e50af497-...",
  "visitId": "24702de6-...",
  "senderRole": "user",
  "kind": "photo",
  "body": "",
  "photo": { "bytes": 1843200, "mime": "image/jpeg" },
  "createdAt": "...",
  "clientMsgId": "c-abc123"
}
```

**`path`는 내보내지 않는다.** 화면은 `messageId`로 받아 오면 되고, 저장소 안의 자리를
클라이언트가 알 이유가 없다.

## 화면

양쪽이 같은 `StaffChatScreen`을 쓰므로 **한 번 만들면 둘 다 된다.**

- 입력칸 왼쪽에 사진 아이콘. 누르면 기기의 사진 고르기가 열린다
- 고르면 **바로 올라간다.** 미리보기를 두고 "보내기"를 한 번 더 누르게 하지 않는다 —
  누를 것이 늘면 저리터러시 사용자가 중간에 멈춘다
- 올라가는 동안 말풍선 자리에 진행 표시. 실패하면 그 자리에 "보내지 못했어요 · 다시"
- 사진 말풍선을 누르면 전체 화면으로 크게 본다

**웹에서는 `<input type="file">`이고 앱에서는 `expo-image-picker`다.** 앱 쪽 라이브러리는
아직 없으므로, **이번에는 웹만 만든다** — 심사·시연이 웹이고(§2.6) 새 의존성을 하나 더
들이는 것은 별개 결정이다.

## 실패와 경계

| 무엇 | 어떻게 |
|---|---|
| 5MB 초과 | 413. **자르지 않는다** — 잘린 사진을 보낸 사람은 다 갔다고 믿는다 |
| 형식이 아님 (HEIC 등) | 415. "다른 형식으로 보내 주세요"라고 안내한다 |
| 저장소는 됐는데 DB가 실패 | 올린 파일을 지우고 실패로 돌려준다. 안 지우면 아무도 못 보는 파일이 쌓인다 |
| DB는 됐는데 저장소가 실패 | 저장소를 먼저 올리고 DB를 뒤에 쓴다. 이 경우가 생기지 않는다 |
| 복호화 실패 | 그 사진만 "사진을 열지 못했어요"로 둔다. 대화는 계속 보인다 |
| 같은 사진을 두 번 보냄 | `clientMsgId`로 재전송을 거른다. 글과 같은 규칙이다 |
| 옛 화면이 사진 메시지를 받음 | `kind`를 모르니 `text`로 보고 빈 말풍선을 그린다. 대화는 안 깨진다 |

## 무엇을 시험하는가

**바이트 암호화**
- 넣은 그대로 되돌아온다
- 다른 키로는 못 읽는다 (`CryptoError`)
- 한 바이트를 바꾸면 못 읽는다 — GCM이 무결성까지 본다
- 빈 바이트열도 다룬다

**받기 전 거르기**
- 남의 방에 올리면 거절
- 닫힌 방에 올리면 거절
- 5MB 초과 → 413
- 선언하지 않은 형식 → 415

**보기**
- 방 참여자가 아니면 거절
- 없는 `messageId`면 404
- 사진이 아닌 메시지의 id로 부르면 404

**딸려 지워지는가**
- 계정을 지우면 저장소의 그 앞자리도 비어 있다

## 하지 않는 것

- **EXIF를 지우지 않는다** (2026-08-26 결정). 공단 담당자와 주고받는 사진이라는 판단이며,
  촬영 위치가 사진에 남은 채로 서버에 저장된다는 뜻이다
- **크기를 줄이거나 다시 그리지 않는다.** 이미지 라이브러리를 안 들인다
- **앱(네이티브) 쪽은 이번에 안 만든다.** `expo-image-picker`가 새 의존성이다
- **사진에만 따로 보관 기간을 두지 않는다.** 대화와 같이 간다
- **파기 배치를 이번에 만들지 않는다.** 없다는 사실과 대상이 늘었다는 것만 남긴다
