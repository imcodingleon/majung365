# 채팅에서 방문 시간 확정하기 — 설계

> 마중365 본선. 기획서 §7.1·§7.2·§7.3, 소켓 계약 `Majung-Backend/docs/socket-contract.md`.
> 결정 기록: `_bmad-output/specs/spec-majung-2nd/decision-log-2026-08-26.md`

## 무엇을 만드는가

담당자와 출소자가 **대화하던 자리에서 만날 때를 정한다.** 지금은 담당자가 요청 상세
화면으로 나가 확정해야 하고, 출소자는 그 결과를 알림으로만 받는다. 시간이 안 맞으면
채팅으로 이야기하다가 담당자가 다시 상세 화면으로 가야 한다.

**출소자에게 수락할 길이 없다는 것이 핵심 결함이다.** 상태 기계에는 "담당자가 다른
시간을 제안했어요"(`reschedule_proposed`)가 이미 있고 `제안됨 → 확정` 전이도 열려
있는데, 그 전이를 부를 수 있는 것은 담당자 창구뿐이다. 출소자는 제안을 보기만 한다.

## 왜 지금 구조에 얹는가

상태 전이 검증은 `VisitUseCase`에 모여 있다. 이것을 소켓으로 옮기거나 복제하면 **상태를
바꾸는 규칙이 두 곳에 생긴다.** 이 프로젝트에서 오늘 하루에만 같은 모양의 결함을 여섯 건
고쳤다 — 완료 저장(CORS), 챗 토큰, 설문 답변, 홈 위치, 알림 읽음, 상담 목록. 전부
"한쪽만 만들고 짝을 안 봄"이었다.

그래서 **상태는 REST가 바꾸고, 소켓은 "바뀌었다"만 알린다.**

## 상태

새 상태를 만들지 않는다. 기존 전이표를 그대로 쓴다.

```
확인함  ──제안──▶  제안됨  ──수락──▶  확정
확정    ──재조율──▶ 제안됨
```

- **확정 뒤에도 바꿀 수 있다.** 확정하고 나서 사정이 생기는 일이 실제로 있다. 같은
  제안 흐름을 다시 타면 되고, 확정 시각이 갱신된다
- 취소는 어느 상태에서나 가능하며 전이표가 그대로 막고 허용한다

## 창구

### 담당자가 제안한다 — 기존 `PATCH /api/staff/visits/{id}`

새 창구를 만들지 않는다. 이미 `status=reschedule_proposed` + `proposed_at`을 받는다.

**바뀌는 것 하나: `meeting_place` 검증.**

| 지금 요청에 장소가 | 제안할 때 |
|---|---|
| 있다 (한 번 확정한 적 있음) | 안 보내도 된다. 있는 것을 그대로 쓴다 |
| 없다 (확인만 한 상태) | **함께 보내야 한다.** 없으면 400 |

장소 없는 확정은 §7.1이 막는다. 제안을 수락하면 곧바로 확정이 되므로, 그 시점에
장소가 없으면 수락 자체가 실패한다 — **실패를 수락하는 사람 쪽으로 미루지 않는다.**

### 출소자가 수락한다 — `POST /api/visits/{id}/accept` (신설)

몸통이 없다. 서버가 이미 아는 것으로 확정한다.

```
확정 시각 ← proposed_at
만날 장소 ← meeting_place (이미 있다. 없으면 제안 단계에서 막혔다)
담당자    ← 제안한 담당자 (서버가 기록해 둔 값)
```

**출소자가 시각을 보내지 않는다.** 보내게 하면 화면이 옛 제안을 들고 있다가 이미 바뀐
시각으로 확정할 수 있다. 서버가 아는 것만 쓴다.

> **⚠ 조용히 지워지는 자리가 있다.** `SupabaseVisitRepository.update_status`는 상태가
> `CONFIRMED`일 때 `assigned_staff_id`와 `meeting_place`를 **넘어온 값으로 무조건
> 덮어쓴다.** 일부러 그렇게 두었다 — "확정에는 담당자와 장소가 반드시 함께 간다".
>
> 그래서 수락 유스케이스는 **지금 값을 읽어 그대로 다시 넣어야 한다.** 안 그러면
> 출소자가 수락하는 순간 담당자 이름과 장소가 `None`이 되고, 화면에는 "확정되었어요"만
> 남고 **누구를 어디서 만나는지가 사라진다.** 오류도 안 난다.
>
> 저장소의 규칙은 그대로 둔다. 부르는 쪽이 채워 넣는다.

거절 조건:
- 남의 요청이면 `not_found` (없는 요청과 같은 문구 — 구분해 주면 남의 id를 찾는 데 쓰인다)
- `reschedule_proposed`가 아니면 `bad_transition`
- `proposed_at`이 비어 있으면 `no_time`

### "어려워요"는 창구가 없다

거절 버튼은 상태를 바꾸지 않는다. **배너를 접고 대화로 돌아간다.** 왜 어려운지는
사람이 말해야 하는 것이고, "거절됨" 상태를 만들면 담당자가 이유를 모른 채 다시
제안하게 된다.

## 소켓

**서버→클라 이벤트 하나만 늘린다.** 클라→서버는 늘리지 않는다.

### `visit_updated`

```json
{
  "visitId": "24702de6-...",
  "status": "reschedule_proposed",
  "proposedAt": "2026-08-28T05:00:00+00:00",
  "confirmedFor": null,
  "meetingPlace": "2층 상담실"
}
```

- 표기는 소켓 관례대로 camelCase다 (계약 문서 "왜 REST와 표기가 다른가")
- 상태를 바꾼 **REST 핸들러가 방송한다.** 소켓 서버는 받아서 흘려보내기만 한다
- 방에 아무도 없어도 실패하지 않는다

**소켓은 빠르게 하는 장치이지 정확성의 근거가 아니다.** 끊겨서 이 이벤트를 놓쳐도
채팅을 닫을 때 `visit.reload()`가 돌아 화면이 맞춰진다(이미 그렇게 동작한다).

## 화면

### 담당자 채팅

입력칸 위에 **"만날 때 제안하기"** 한 줄.

```
┌────────────────────────────────┐
│  만날 때 제안하기               │
└────────────────────────────────┘
│ 메시지를 적으세요        [ ➤ ] │
```

누르면 시트가 올라온다. **기존 `VisitTimeField`를 그대로 쓴다** — 상세 화면의 확정과
같은 부품, 같은 규칙이다. 장소 칸은 요청에 장소가 없을 때만 나온다.

### 출소자 채팅

제안이 살아 있는 동안 대화 위에 배너가 붙는다.

```
┌────────────────────────────────┐
│ 담당자가 이때를 제안했어요        │
│ 8월 28일 (금) 오후 2시           │
│ 2층 상담실                      │
│ [ 좋아요 ]      [ 어려워요 ]     │
└────────────────────────────────┘
```

- **"좋아요"가 확정이다.** 누르면 배너가 사라지고 대화에 "방문이 확정되었어요"가 뜬다
- "어려워요"는 배너만 접는다. 다시 보고 싶으면 알림 탭에 남아 있다
- 배너는 `status === "reschedule_proposed"`일 때만 그린다

### 대화 흐름에는 남기지 않는다

제안·수락을 메시지로 저장하지 않는다.

- `visit_message`에 `kind` 컬럼을 더하는 마이그레이션이 필요해진다
- 지난 제안은 **알림 탭에 날짜와 함께 쌓인다**(결정 G-5) — 되짚을 자리가 이미 있다
- 대화에 시스템 말풍선이 섞이면 "누가 말했나"가 흐려진다. `senderRole`을 역할로만 둔
  이유가 그것이다

## 실패와 경계

| 무엇 | 어떻게 |
|---|---|
| 지난 시각 제안 | 400. 이미 지난 때로 확정되면 아무도 안 나타난다 |
| 장소 없이 제안 | 400. 수락하는 쪽으로 실패를 미루지 않는다 |
| 수락하려는데 취소됨 | 전이표가 막는다. 배너가 사라지고 취소 사유가 보인다 |
| 수락하려는데 새 제안이 옴 | 서버가 아는 `proposed_at`으로 확정된다. 화면이 든 옛 값을 안 쓴다 |
| 소켓 끊김 | 채팅을 닫을 때 다시 읽는다. 이벤트는 빠르게 하는 장치일 뿐이다 |
| 담당자가 둘이 동시에 제안 | 나중 것이 이긴다. `proposed_at`은 한 값이고 덮어쓴다 |

## 무엇을 시험하는가

전부 계산·유스케이스 수준이다. 화면은 배포 후 번들로 대조한다.

**전이**
- 제안됨 → 수락 → 확정. `confirmed_for`가 `proposed_at`과 같다
- 확인함에서 바로 수락하면 거절 (`bad_transition`)
- 취소된 뒤 수락하면 거절
- 확정 → 재조율 → 수락으로 시각이 갱신된다

**장소**
- 장소 없는 요청에 장소 없이 제안 → 400
- 장소 없는 요청에 장소와 함께 제안 → 성공, 그 장소로 확정된다
- 장소 있는 요청에 장소 없이 제안 → 성공, 있던 장소를 쓴다

**수락해도 지워지지 않는다** — 위의 ⚠ 자리다. 이것이 빠지면 오류 없이 값만 사라진다.
- 장소가 있는 요청을 출소자가 수락 → **장소가 그대로 남아 있다**
- 담당자가 배정된 요청을 출소자가 수락 → **담당자 이름이 그대로 남아 있다**

**남의 것**
- 남의 요청을 수락 → `not_found` (없는 요청과 같은 문구)

**시각**
- 지난 시각 제안 → 400
- `proposed_at`이 없는데 수락 → `no_time`

## 하지 않는 것

- **새 상태를 만들지 않는다.** "거절됨"을 두면 담당자가 이유를 모른다
- **소켓으로 상태를 바꾸지 않는다.** 규칙이 두 곳에 생긴다
- **제안을 메시지로 저장하지 않는다.** 마이그레이션이 필요하고 얻는 것이 알림 탭과 겹친다
- **출소자가 먼저 제안하는 길은 이번에 안 만든다.** 둘이 동시에 제안하는 경우까지
  다뤄야 하고, 지금 겪는 문제는 그것이 아니다
