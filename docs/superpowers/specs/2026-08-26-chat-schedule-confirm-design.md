# 채팅에서 방문 시간 확정하기 — 설계

> 마중365 본선. 기획서 §7.1·§7.2·§7.3, 소켓 계약 `Majung-Backend/docs/socket-contract.md`.
> 결정 기록: `_bmad-output/specs/spec-majung-2nd/decision-log-2026-08-26.md`

## 무엇을 만드는가

담당자와 출소자가 **대화하던 자리에서 만날 때를 정한다.** 지금은 담당자가 요청 상세
화면으로 나가 확정해야 하고, 출소자는 그 결과를 알림으로만 받는다. 시간이 안 맞으면
채팅으로 이야기하다가 담당자가 다시 상세 화면으로 가야 한다.

**출소자에게 수락할 길이 없다는 것이 핵심 결함이다.** 상태 기계에는 "담당자가 다른
시간을 제안했어요"(`reschedule_proposed`)가 이미 있고 `제안됨 → 확정` 전이도 열려
있는데, 그 전이를 부를 수 있는 것은 담당자 창구뿐이다. 출소자는 제안을 보기만 한다.

## 왜 지금 구조에 얹는가

상태 전이 검증은 `VisitUseCase`에 모여 있다. 이것을 소켓으로 옮기거나 복제하면 **상태를
바꾸는 규칙이 두 곳에 생긴다.** 이 프로젝트에서 오늘 하루에만 같은 모양의 결함을 여섯 건
고쳤다 — 완료 저장(CORS), 챗 토큰, 설문 답변, 홈 위치, 알림 읽음, 상담 목록. 전부
"한쪽만 만들고 짝을 안 봄"이었다.

그래서 **상태는 REST가 바꾸고, 소켓은 "바뀌었다"만 알린다.**

## 상태

새 상태를 만들지 않는다. 기존 전이표를 그대로 쓴다.

```
확인함  ──제안──▶  제안됨  ──수락──▶  확정
확정    ──재조율──▶ 제안됨
```

- **확정 뒤에도 바꿀 수 있다.** 확정하고 나서 사정이 생기는 일이 실제로 있다. 같은
  제안 흐름을 다시 타면 되고, 확정 시각이 갱신된다
- 취소는 어느 상태에서나 가능하며 전이표가 그대로 막고 허용한다

## 창구

### 담당자가 제안한다 — 기존 `PATCH /api/staff/visits/{id}`

새 창구를 만들지 않는다. 이미 `status=reschedule_proposed` + `proposed_at`을 받는다.

**바뀌는 것 하나: `meeting_place` 검증.**

| 지금 요청에 장소가 | 제안할 때 |
|---|---|
| 있다 (한 번 확정한 적 있음) | 안 보내도 된다. 있는 것을 그대로 쓴다 |
| 없다 (확인만 한 상태) | **함께 보내야 한다.** 없으면 400 |

장소 없는 확정은 §7.1이 막는다. 제안을 수락하면 곧바로 확정이 되므로, 그 시점에
장소가 없으면 수락 자체가 실패한다 — **실패를 수락하는 사람 쪽으로 미루지 않는다.**

### 출소자가 수락한다 — `POST /api/visits/{id}/accept` (신설)

몸통이 없다. 서버가 이미 아는 것으로 확정한다.

```
확정 시각 ← proposed_at
만날 장소 ← meeting_place (이미 있다. 없으면 제안 단계에서 막혔다)
담당자    ← 제안한 담당자 (서버가 기록해 둔 값)
```

**출소자가 시각을 보내지 않는다.** 보내게 하면 화면이 옛 제안을 들고 있다가 이미 바뀐
시각으로 확정할 수 있다. 서버가 아는 것만 쓴다.

> **⚠ 조용히 지워지는 자리가 있다.** `SupabaseVisitRepository.update_status`는 상태가
> `CONFIRMED`일 때 `assigned_staff_id`와 `meeting_place`를 **넘어온 값으로 무조건
> 덮어쓴다.** 일부러 그렇게 두었다 — "확정에는 담당자와 장소가 반드시 함께 간다".
>
> 그래서 수락 유스케이스는 **지금 값을 읽어 그대로 다시 넣어야 한다.** 안 그러면
> 출소자가 수락하는 순간 담당자 이름과 장소가 `None`이 되고, 화면에는 "확정되었어요"만
> 남고 **누구를 어디서 만나는지가 사라진다.** 오류도 안 난다.
>
> 저장소의 규칙은 그대로 둔다. 부르는 쪽이 채워 넣는다.

거절 조건:
- 남의 요청이면 `not_found` (없는 요청과 같은 문구 — 구분해 주면 남의 id를 찾는 데 쓰인다)
- `reschedule_proposed`가 아니면 `bad_transition`
- `proposed_at`이 비어 있으면 `no_time`

### "어려워요"는 창구가 없다

거절 버튼은 상태를 바꾸지 않는다. **배너를 접고 대화로 돌아간다.** 왜 어려운지는
사람이 말해야 하는 것이고, "거절됨" 상태를 만들면 담당자가 이유를 모른 채 다시
제안하게 된다.

## 저장 — 마이그레이션 `0010_visit_message_kind.sql`

```sql
alter table visit_message
  add column if not exists kind text not null default 'text'
    check (kind in ('text', 'proposed', 'confirmed', 'cancelled')),
  add column if not exists schedule jsonb;

alter table visit_message
  alter column body_enc drop not null;
```

**`body_enc`의 not null을 푼다.** 약속 카드에는 사람이 쓴 본문이 없다. 빈 문자열을
암호화해 넣으면 "본문이 있는 척"이 되고, 그것을 읽는 코드가 빈 말풍선을 그린다.

`schedule`에 담기는 것:

```json
{ "at": "2026-08-28T05:00:00+00:00", "place": "2층 상담실", "staffName": "최다은" }
```

**평문이다.** 같은 값이 `visit_request.confirmed_for`·`meeting_place`에 이미 평문으로
있어서, 한쪽만 암호화하면 얻는 것 없이 읽는 길만 둘로 갈린다. 본문(`body_enc`)을
암호화하는 이유는 사적인 사정이 오가기 때문이고, 약속 시각과 창구 이름은 그 성격이 다르다.

`sender_role`은 **그 일을 한 사람의 역할**을 그대로 넣는다 — 담당자가 제안하면 `staff`,
출소자가 수락하면 `user`다. 카드를 가운데에 세울지는 `kind`가 정하지 `sender_role`이
정하지 않는다. 역할을 "누가 말했나"의 기록으로 둔 뜻을 지킨다.

## 소켓

**클라→서버는 늘리지 않는다.** 서버→클라만 손댄다.

### `new_message` — 필드 둘이 는다

약속 카드도 메시지다. **새 이벤트를 만들지 않는다** — 만들면 화면이 대화를 두 갈래로
받아 순서를 스스로 맞춰야 하고, 그 자리에서 카드가 엉뚱한 데 끼어든다.

```json
{
  "id": "...",
  "visitId": "...",
  "senderRole": "staff",
  "kind": "proposed",
  "body": "",
  "schedule": { "at": "...", "place": "2층 상담실", "staffName": "최다은" },
  "createdAt": "...",
  "clientMsgId": ""
}
```

`kind`가 없으면 `"text"`로 본다 — **옛 화면이 그대로 돈다.** 약속 카드는 본문이 비어
있어 말풍선 하나가 빈 채로 보이지만, 대화가 깨지지는 않는다.

`join` 응답의 `messages`에도 같은 두 필드가 실린다.

### `visit_updated`

```json
{
  "visitId": "24702de6-...",
  "status": "reschedule_proposed",
  "proposedAt": "2026-08-28T05:00:00+00:00",
  "confirmedFor": null,
  "meetingPlace": "2층 상담실"
}
```

- 표기는 소켓 관례대로 camelCase다 (계약 문서 "왜 REST와 표기가 다른가")
- 상태를 바꾼 **REST 핸들러가 방송한다.** 소켓 서버는 받아서 흘려보내기만 한다
- 방에 아무도 없어도 실패하지 않는다

**소켓은 빠르게 하는 장치이지 정확성의 근거가 아니다.** 끊겨서 이 이벤트를 놓쳐도
채팅을 닫을 때 `visit.reload()`가 돌아 화면이 맞춰진다(이미 그렇게 동작한다).

## 화면

### 담당자 채팅

입력칸 위에 **"만날 때 제안하기"** 한 줄.

```
┌────────────────────────────────┐
│  만날 때 제안하기               │
└────────────────────────────────┘
│ 메시지를 적으세요        [ ➤ ] │
```

누르면 시트가 올라온다. **기존 `VisitTimeField`를 그대로 쓴다** — 상세 화면의 확정과
같은 부품, 같은 규칙이다. 장소 칸은 요청에 장소가 없을 때만 나온다.

### 출소자 채팅

대화 흐름의 제안 카드에 버튼이 붙는다. 따로 배너를 두지 않는다 — **약속이 대화 안에
있어야 위로 올려 봤을 때 이야기와 함께 읽힌다.**

- **"좋아요"가 확정이다.** 누르면 그 아래에 "만남이 예약되었어요" 카드가 새로 선다
- **"어려워요"는 아무것도 바꾸지 않는다.** 버튼만 사라지고 대화로 돌아간다. 왜 어려운지는
  사람이 말해야 하고, "거절됨" 상태를 만들면 담당자가 이유를 모른 채 다시 제안하게 된다
- 버튼은 **마지막 제안 카드에만** 그린다. 그 판정은 저장하지 않고 지금 요청 상태로 한다

### 대화 흐름에 약속 카드로 남는다

**중고 거래 앱에서 만날 약속을 잡는 것과 같은 모양이다.** 제안·확정·취소가 대화 흐름에
카드로 서고, 위로 올려 보면 언제 무엇을 정했는지 그대로 보인다.

```
  담당자  8월 28일에 오실 수 있을까요?

        ┌──────────────────────────┐
        │  만날 때를 제안했어요       │
        │  8월 28일 (금) 오후 2시    │
        │  2층 상담실               │
        │  [ 좋아요 ]  [ 어려워요 ]  │
        └──────────────────────────┘

  나      네 그때 갈게요

        ┌──────────────────────────┐
        │  ✓ 만남이 예약되었어요      │
        │  8월 28일 (금) 오후 2시    │
        │  2층 상담실 · 최다은        │
        └──────────────────────────┘
```

카드는 좌우 어느 쪽에도 붙지 않고 **가운데에 선다.** 누가 보낸 말이 아니라 둘 사이에
정해진 일이기 때문이다.

**버튼은 저장하지 않는다.** 카드에 "답했음" 같은 값을 넣으면 상태와 어긋날 수 있다.
버튼을 그릴지는 **지금 요청 상태가 `reschedule_proposed`이고 이 카드가 마지막 제안일
때**로 판정한다. 지난 제안 카드에는 버튼이 없다.

## 실패와 경계

| 무엇 | 어떻게 |
|---|---|
| 지난 시각 제안 | 400. 이미 지난 때로 확정되면 아무도 안 나타난다 |
| 장소 없이 제안 | 400. 수락하는 쪽으로 실패를 미루지 않는다 |
| 수락하려는데 취소됨 | 전이표가 막는다. 배너가 사라지고 취소 사유가 보인다 |
| 수락하려는데 새 제안이 옴 | 서버가 아는 `proposed_at`으로 확정된다. 화면이 든 옛 값을 안 쓴다 |
| 소켓 끊김 | 채팅을 닫을 때 다시 읽는다. 이벤트는 빠르게 하는 장치일 뿐이다 |
| 담당자가 둘이 동시에 제안 | 나중 것이 이긴다. `proposed_at`은 한 값이고 덮어쓴다. 카드는 둘 다 남고 **버튼은 마지막 것에만** 붙는다 |
| 카드 저장은 됐는데 상태 변경이 실패 | 상태를 먼저 바꾸고 카드를 뒤에 넣는다. 반대로 하면 **약속했다고 적혀 있는데 실제로는 아닌** 대화가 남는다 |
| 카드 저장이 실패 | 상태는 이미 바뀌었다. 대화에 카드가 빠질 뿐이고 알림과 요청 화면은 맞다. 로그만 남기고 요청은 성공으로 돌려준다 |
| 옛 화면이 새 메시지를 받음 | `kind`를 모르니 `text`로 보고 빈 말풍선을 그린다. 대화는 안 깨진다 |

## 무엇을 시험하는가

전부 계산·유스케이스 수준이다. 화면은 배포 후 번들로 대조한다.

**전이**
- 제안됨 → 수락 → 확정. `confirmed_for`가 `proposed_at`과 같다
- 확인함에서 바로 수락하면 거절 (`bad_transition`)
- 취소된 뒤 수락하면 거절
- 확정 → 재조율 → 수락으로 시각이 갱신된다

**장소**
- 장소 없는 요청에 장소 없이 제안 → 400
- 장소 없는 요청에 장소와 함께 제안 → 성공, 그 장소로 확정된다
- 장소 있는 요청에 장소 없이 제안 → 성공, 있던 장소를 쓴다

**수락해도 지워지지 않는다** — 위의 ⚠ 자리다. 이것이 빠지면 오류 없이 값만 사라진다.
- 장소가 있는 요청을 출소자가 수락 → **장소가 그대로 남아 있다**
- 담당자가 배정된 요청을 출소자가 수락 → **담당자 이름이 그대로 남아 있다**

**남의 것**
- 남의 요청을 수락 → `not_found` (없는 요청과 같은 문구)

**시각**
- 지난 시각 제안 → 400
- `proposed_at`이 없는데 수락 → `no_time`

**약속 카드**
- 제안하면 `kind="proposed"` 카드가 대화에 쌓이고 `schedule`에 때·장소가 들어간다
- 수락하면 `kind="confirmed"` 카드가 그 뒤에 쌓인다. **앞 카드를 고치지 않는다**
- 취소하면 `kind="cancelled"` 카드가 쌓인다
- 지난 대화를 다시 불러도 카드가 그대로 온다 (`join` 응답·`history`)
- **버튼 판정**: 마지막 제안이고 상태가 `reschedule_proposed`면 참, 그 밖에는 거짓
  — 제안이 둘 쌓인 뒤 앞 카드에는 버튼이 없다
- 본문이 빈 카드가 미리보기(`last_message`)를 차지하지 않는다 — 목록에 빈 줄이 뜬다

## 하지 않는 것

- **새 상태를 만들지 않는다.** "거절됨"을 두면 담당자가 이유를 모른다
- **소켓으로 상태를 바꾸지 않는다.** 규칙이 두 곳에 생긴다
- **약속 카드에 "답했음"을 저장하지 않는다.** 버튼을 그릴지는 지금 요청 상태로 판정한다.
  저장하면 상태와 어긋날 수 있고, 어긋나면 지난 카드의 버튼이 다시 살아난다
- **새 소켓 이벤트로 카드를 보내지 않는다.** `new_message`에 필드를 더한다. 갈래가
  둘이면 화면이 순서를 스스로 맞춰야 하고, 그 자리에서 카드가 엉뚱한 데 끼어든다
- **출소자가 먼저 제안하는 길은 이번에 안 만든다.** 둘이 동시에 제안하는 경우까지
  다뤄야 하고, 지금 겪는 문제는 그것이 아니다
- **사진 첨부는 이 문서에 넣지 않는다.** 저장소·업로드·보관 파기가 통째로 딸린 별개
  주제이며, 마이그레이션 0005가 "이미지를 넣지 않는다"고 적어 둔 결정을 뒤집는 일이다.
  따로 설계한다
